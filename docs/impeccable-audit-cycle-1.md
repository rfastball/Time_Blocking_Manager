## Implementation Integrity 판정

**Fail — 입력 보존의 두 비동기 경로가 제품의 저장 안전성 약속을 지키지 못한다.** B/D 화면 구조, 날짜·배치 모델, 로컬 저장 상태 표현은 제품에 맞게 일관되어 있다. 전면 재설계 대상은 아니다. 그러나 캡처 재시도와 완료 상태 변경의 성공 콜백이 요청 이후의 새 입력을 덮어쓸 수 있다.

## 상세 지적

### F1. [P1] 이전 캡처 재시도 성공이 새 캡처 초안을 지움

- 위치: `src/main.ts:118`–`127` (`submitCapture`), `src/main.ts:114`, `src/main.ts:49`, `src/queue.ts:17`–`23`.
- 차원: Implementation Integrity.
- 재현 경로: A를 캡처하다 저장 실패 → 입력이 다시 활성화됨 → 사용자가 B로 내용을 바꿈 → 저장 환경을 복구하고 실패한 A를 재시도 → A의 기존 성공 콜백 실행.
- 근거: 실패한 작업은 queue에 남아 재시도된다. 성공 콜백은 현재 입력의 명령/버전을 확인하지 않고 `capture=''`, 입력 value 비우기, 빈 초안 저장, 캡처창 숨기기를 실행한다. 입력 이벤트는 새 명령을 위한 `captureCommand=null`만 수행한다.
- 영향: B가 저장되지 않은 채 입력과 초안에서 사라진다. 캡처창에서는 사라진 상태로 창까지 숨겨져 사용자가 놓치기 쉽다.
- 권고: 요청 당시 명령 identity/입력 버전과 현재 상태가 같은 경우에만 비우고 숨긴다. 이전 요청의 성공과 더 최신 입력이 남아 있는 상태를 구분한다.
- 기준: PRODUCT.md의 초안 보존·저장 성공 구분 약속. WCAG 항목으로 포장하지 않는 데이터 보존 결함.
- 권장 명령: `$impeccable harden`.

### F2. [P1] 완료 저장 중 입력한 편집 내용을 성공 콜백이 덮어씀

- 위치: `src/main.ts:234` (`editor-complete`), 비교할 기존 보호 로직 `src/main.ts:241`–`245`.
- 차원: Implementation Integrity.
- 재현 경로: 항목 상세에서 완료로 표시 → 저장 응답을 기다리는 동안 제목이나 본문 편집 → 완료 상태 변경 응답 도착.
- 근거: 완료 요청 시작 시에는 editorDirty를 확인하지만 대기 중 입력을 막거나 버전을 기록하지 않는다. 성공 시 `editor={...snapshot task}` 후 `renderEditor()`로 폼을 다시 만든다. 일반 변경 저장에는 editorSequence 보호가 있으나 이 경로에는 없다.
- 영향: 응답을 기다리며 입력한 제목/메모가 화면 및 editor 상태에서 사라진다. 후속 초안 저장이 이전 내용을 확정할 위험도 있다.
- 권고: 해당 요청 이후 편집 여부를 확인하고 현재 초안을 보존하면서 revision/completed만 반영하거나, 짧은 완료 요청 동안 충돌하는 입력만 명확히 잠근다. 기존 저장 경로의 보호 방식과 일관되게 처리한다.
- 기준: PRODUCT.md의 원본/초안 보존 약속.
- 권장 명령: `$impeccable harden`.

### F3. [P2] 전체 DOM 갱신이 포커스와 시간표 스크롤을 초기화함

- 위치: `src/main.ts:134`, `157`–`158`, `210`, `289`.
- 차원: Accessibility / Performance.
- 재현: 키보드로 날짜를 선택하면 renderContent가 선택한 버튼을 제거한다. 부모의 Chromium 미리보기 실행에서 activeElement=BODY를 확인했다. 시간표를 아래로 스크롤하고 매분 갱신을 맞으면 새 timeline-scroll 요소가 만들어져 내부 스크롤 위치가 초기화되는 코드 경로도 존재한다. 키보드 길이 조절 성공 후에도 컨트롤이 교체된다.
- 영향: 날짜 선택·길이 조절을 이어가려는 키보드 사용자는 현재 위치를 다시 찾아야 한다. 늦은 시간 업무를 보고 있을 때 주기적인 갱신이 읽던 구간을 바꾼다.
- 권고: 사용자 동작 후 동일 의미 컨트롤로 포커스를 복원하고 내부 스크롤 위치를 유지한다. 매분 현재 시각선 갱신은 전체 화면 재생성을 피한다.
- 기준: WCAG 2.4.3의 예측 가능한 포커스 순서 관련. 전체 접근성 적합성 판정은 아님.
- 권장 명령: `$impeccable harden`, 필요한 부분만 `$impeccable optimize`.

### F4. [P2] 최소 지원 창에서 Inbox와 시간표를 함께 조작하기 어려움

- 위치: `src/style.css:3`의 1250px 이하 with-inbox 배치, `src/style.css:4`의 960px 이하 레이아웃, `src/main.ts:167`–`199`의 드래그.
- 차원: Responsive Design.
- 실행 근거: 부모의 Chromium 미리보기 960×640 크기 에뮬레이션에서 Inbox 시작 y=882, 시간표 y=288–658. Inbox는 달력/시간표 다음 행으로 배치되어 기본 viewport에 둘을 함께 놓을 수 없다. 드래그 구현에는 스크롤 경계에서의 자동 이동 경로가 없다.
- 영향: 지원 최소 창에서 주요 동작인 Inbox→시간표 배치에 별도 스크롤 조작 또는 상세 폼 우회가 필요하다. 배치 자체가 불가능하다고 단정하지 않는다.
- 권고: 이 폭에서 Inbox를 접근 가능한 drawer/고정 영역으로 유지하거나, 배치 대상을 보면서 조작할 수 있는 축약 구성을 사용한다. 승인된 B/D의 역할과 색상을 유지한다.
- 기준: 제품의 960×640 Windows 지원 범위와 Inbox 드래그 배치 요구.
- 권장 명령: `$impeccable adapt`.

### F5. [P2] 실패 요청이 남아 있을 때 변경 저장이 설명 없이 무반응

- 위치: `src/main.ts:241`–`242`, 복구 컨트롤 `src/main.ts:51`–`55`.
- 차원: Implementation Integrity / Accessibility.
- 재현: 상세 저장을 배치 충돌로 실패시킴 → 값을 고쳐 변경 저장 클릭.
- 근거: queue.failed가 남아 있으면 saveEditor는 즉시 return한다. 변경 저장 버튼은 활성 상태이고 클릭에 따른 새 설명도 없다. modal 안에는 별도의 실패 요청 해제 버튼이 존재한다.
- 영향: 사용자는 올바르게 수정해도 저장 버튼이 동작하지 않는 이유를 알아내야 한다. 복구 컨트롤이라는 우회로가 있어 P1이 아닌 P2로 분류했다.
- 권고: 실패 요청이 남았다는 점과 필요한 다음 동작을 저장 버튼에서 안내하거나, 안전하게 실패 요청을 해제하고 현재 수정본을 새 요청으로 보내는 흐름으로 일관시킨다. 조용한 return만 남기지 않는다.
- 기준: 문제와 복구 방법을 설명하는 제품 오류 상태 요구. 특정 WCAG 실패로 단정하지 않음.
- 권장 명령: `$impeccable harden` 또는 `$impeccable clarify`.

### F6. [P2] 최소 길이 15분 블록에서 제목과 크기 조절 손잡이가 겹침

- 위치: `src/main.ts:152`, `src/style.css:2`의 `.time-block`, `.block-title`, `.resize-handle`.
- 차원: Responsive Design / Accessibility.
- 재현: 계획 화면에서 15분 길이 업무를 표시.
- 근거: 1.2px/분이므로 블록은 18px 높이이다. 내부 제목 버튼의 상하 padding 합계 8px와 12px 글자가 이 안에 들어가며, 아래쪽 8px 높이 resize 손잡이가 겹친다. overflow:hidden도 적용되어 있다. UX 검토의 겹침 관찰과 일치한다.
- 영향: 정상 지원 길이인 15분 항목에서 제목 읽기와 상세 열기/크기 조절 조작이 불편하다. 시간 위치·길이는 바꾸지 않고 해결해야 한다.
- 권고: 짧은 블록에 맞는 compact 제목 padding/line-height와 별도의 손잡이 위치 또는 선택 후 resize 조작을 제공한다. 분당 높이와 실제 시간 의미는 유지한다.
- 기준: 15분 최소 길이 제품 요구와 주요 조작의 명확성. Windows 일반 버튼에 44px를 요구하는 지적이 아님.
- 권장 명령: `$impeccable adapt` 또는 `$impeccable polish`.

## 반복 패턴

1. 비동기 응답이 요청 당시 입력과 현재 입력을 구분하지 않는 일부 경로가 있다. 일반 편집 저장의 sequence 보호를 다른 경로에도 일관되게 적용할 필요가 있다.
2. 전체 innerHTML 교체에 의존해 일시적인 사용자 상태인 포커스와 스크롤을 잃는다. 새로운 프레임워크 도입 없이 갱신 범위와 상태 복원만 좁히면 된다.
3. CSS 색상 토큰은 부분 적용 상태다. 현재 사용자 영향이 확인되지 않은 색상 리터럴을 별도 P3 목록으로 늘리지 않았다.

## 유지할 점

- B 오늘 목록+시간표 / D 월간+선택일+Inbox 구조와 승인된 기본 시각 체계가 유지된다.
- capture 입력 라벨, 아이콘 버튼 이름, 날짜 aria-label/pressed/current, native dialog, focus-visible, reduced-motion 조건이 있다.
- 고정 상태 영역과 modal 내부 실패 복구 버튼이 존재하며, 현재 증거에서는 실패 입력을 유지한다.
- Rust가 모든 쓰기를 검증하고 요청 identity/revision/epoch를 사용한다. 창을 닫을 때 프로세스를 종료하지 않으며, 명시적 종료는 busy 상태와 저장된 초안까지 확인한다.
- 브라우저 샘플 데이터는 미리보기로 명확히 표시한다. 저장 실패를 성공으로 표시하거나 빈 DB로 대체하지 않는다.
- 소규모 번들과 시스템 글꼴로 분리망에서 불필요한 원격 리소스를 요구하지 않는다.

## 권장 실행 순서

## Cycle 1 수정 후 제한적 재검증

2026-10-08, 부모의 한 묶음 수정 이후 **F1–F6만 재검증**했다. 새로운 전체 감사나 WCAG AA 적합성 검증은 아니다. 현재 소스를 직접 읽었고, 실행 결과는 아래처럼 출처를 구분했다. 재검증자는 소스를 수정하지 않았다.

DESIGN.md의 18px/16px 타입 항목, 좁은 Inbox 레이아웃, compact 블록 설명 갱신을 직접 확인했다. 최초 detector advisory는 이 문서 수정으로 대조했으며 detector를 다시 실행한 것은 아니다. 부모는 npm 테스트 3개(83.7ms)와 build 통과를 보고했다. Rust 소스 변경이 없어 기존 Rust 테스트 6개는 이번 사이클에서 재실행하지 않았다.
