# BLOKKY 재설계안
## 사건에 반응하는 유동형 업무 배분

**작성일:** 2026-10-10  
**문서 성격:** 제품 의도·개념 구조·사용자 경험을 위한 재설계 제안  
**기준:** 이번 논의에서 합의한 방향. 기존 구현의 완료 상태를 설명하는 문서가 아니다.

> **하루의 가용 공간에 일을 배분하고, 일하는 동안에는 계획을 관리하지 않는다. 끝낸 일은 밖으로 빠져나가고, 남은 일은 지금부터의 공간에 다시 자리 잡는다.**

---

## 1. 재설계의 목적

BLOKKY의 목표는 분 단위의 일정 준수가 아니라 **하루 단위의 투입 대비 유효 산출을 높이는 것**이다. 수행 가능한 시간을 확보하고, 그 시간을 업무에 합리적으로 어림 배분한 뒤, 수행 중에는 업무 자체에 집중하도록 돕는다.

계획은 이 목적을 위한 수단이다. 시간표를 빈틈없이 채우거나 예상한 종료 시각을 정확히 맞추는 행위가 그 자체로 성과가 되지는 않는다. 계획을 유지하는 데 드는 비용이 커진다면, 정교한 계획도 제품의 목적과 어긋날 수 있다.

이번 재설계는 시간의 양을 버리지 않는다. 작업시간을 블록의 크기로 유지해 업무량과 가용량을 비교할 수 있게 한다. 대신 **모든 블록에 정확한 시작 시각을 결정하고 계속 보정해야 하는 부담**을 덜어낸다.

계획과 수행의 분리도 사용자의 행동을 제한하기 위한 것이 아니다. 수행 중에도 순서를 바꾸고, 새 일을 끼워 넣고, 필요하면 시간을 고정할 수 있다. 다만 앱이 그런 판단을 끊임없이 요구하지 않는다.

**핵심 가설은 적은 재조정으로 계획의 유용성을 유지할 수 있다면, 더 많은 주의를 실제 수행에 남길 수 있다는 것이다.** 이 효과는 이후 사용 경험으로 검증해야 한다.

### 기존 제품과의 관계

기존 제품 문서는 캡처·계획·수행·재배치의 흐름, 근무 중 판단의 축소, 입력과 기록의 보호를 지향한다. 이번 제안은 그 의도를 유지하면서 배치 방식을 재정의한다. 기존 문서에서 범위 밖으로 두었던 자동 재배치 중에서도, **완료 이후의 기계적 재배치**를 새로 다룬다. 기존 기능이 이미 이 방식으로 작동한다는 뜻은 아니다. [기존 제품 문서](https://github.com/rfastball/Time_Blocking_Manager/blob/main/PRODUCT.md)

## 2. 합의한 방향과 아직 정하지 않은 것

이 문서는 모든 제안을 같은 강도의 결정으로 취급하지 않는다.

| 구분 | 내용 |
|---|---|
| 합의된 중심 정책 | 유동 작업 완료에 따른 재배치와 수동 재배치 옵션을 제공한다. 시계의 이동이나 블록 경계 통과만으로 재배치하지 않는다. |
| 이번 모델의 단순화 전제 | 유동 블록의 크기는 완료·시간 경과·재배치에 의해 자동으로 바뀌지 않는다. 실제 수행시간을 복원하지 않아도 사용 가능해야 한다. |
| 재설계의 개념 구조 | 날짜에만 배정한 유동계획과 특정 시각을 지키는 고정계획을 구분한다. 완료된 유동 작업은 시간표 밖으로 이동한다. |
| 시각적 탐색 방향 | 위가 이른 시각인 시간축을 유지하고, 상단 흡입구·걸쇠·사건이 있을 때만 작동하는 정렬 장치의 은유를 사용한다. |
| 후속 검토 | 구체적인 화면 구성, 드래그 세부 동작, 배치 알고리즘, 고정 일정 완료 정책, 부분 수행, 저장 구조와 기술 구현을 정한다. |

자동 리사이징을 배제한다는 것은 **사용자가 계획 단계에서 블록 크기를 정하거나 수정할 권한까지 없앤다는 뜻이 아니다.** 이번 단순화의 대상은 수행 경과를 추측해 크기를 자동 보정하는 동작이다.

## 3. 사용자가 이해할 기본 세계

### 3.1 업무시간은 일을 담는 공간이다

하루에는 업무에 사용할 수 있는 공간이 있다. 근무 시작과 종료, 점심·휴식·휴가 등의 불용 구간이 그 공간의 기본 구조를 만든다.

공간이 비어 있다고 반드시 채워야 하는 것은 아니다. 여유는 돌발 업무와 추정 오차를 흡수할 수 있는 몫이며, 사용자가 남겨 둘 수 있어야 한다.

### 3.2 블록의 크기는 배분한 업무시간이다

블록은 제목과 내용뿐 아니라 계획 단계에서 부여한 예상 투입량을 가진다. 크기는 하루의 얼마를 그 일에 배분했는지를 표현한다.

이 크기는 실제 수행시간도, 진행률도 아니다. 60분 블록을 완료했다고 60분을 실제로 일했다는 기록이 생기지 않는다. 30분이 흘렀다고 블록이 절반 완료된 것도 아니다.

### 3.3 세 가지 배치 상태와 하나의 완료 영역

| 구분 | 사용자가 결정한 것 | 공간에서의 의미 |
|---|---|---|
| Inbox·미계획 | 해야 할 일. 크기는 계획할 때 부여하거나 확인한다. | 아직 특정 날짜의 공간을 차지하지 않는다. |
| 유동계획 | 수행할 날짜, 배분량, 상대 순서 | 해당 날짜의 가용 공간에 놓인다. 정확한 시작 시각은 배치 결과다. |
| 고정계획 | 수행할 날짜와 지켜야 하는 시각 | 다른 유동 작업이 변해도 위치를 지키는 예약이다. |
| 완료된 유동 작업 | 해당 일을 끝냈다는 확인 | 앞으로의 시간 공간에서는 빠지고, 완료 영역에 보존된다. |

이 구분은 사용자 경험을 설명하기 위한 것이다. 저장 모델이나 상태 코드의 형태를 확정하지 않는다.

### 3.4 고정 일정은 사용자가 만든 반고정 구조다

워크숍이나 회의처럼 시각이 중요한 작업은 그날 공간의 구조물로 작용한다. 그러나 점심 같은 기본 불용시간과 동일한 것은 아니다. 업무 내용과 완료 여부를 가진 작업이면서, 다른 블록의 배치를 제한하는 예약이다.

걸쇠나 얼린 표면은 **시각이 고정되어 있음**을 표현한다. 편집 불가, 실행 금지, 이동 불가를 뜻하지 않는다. 사용자는 의도적으로 고정 시각을 바꾸거나 고정을 해제할 수 있다.

## 4. 계획은 필요한 만큼만 구체화한다

### 날짜에 놓는 것만으로 계획은 성립한다

사용자는 Inbox의 블록을 특정 날짜에 드래그해 배정한다. 그날의 유동계획이 되며, 별도의 순서를 지정하지 않으면 기존 유동 순서의 뒤에 추가된다.

이후 시간표에 다시 놓지 않아도 된다. 날짜만 배정한 작업을 덜 계획된 작업이나 누락된 일정처럼 표시하지 않는다.

### 순서와 시각 고정은 다른 의도다

유동 블록을 다른 블록의 앞뒤로 옮기는 것은 상대 순서를 정하는 일이다. 특정 시각에 걸쇠를 거는 것은 그 시각을 지키겠다는 별도의 결정이다.

워크숍 블록은 날짜에 먼저 배정한 뒤 고정할 수도 있고, 일간 시간표의 시각을 선택해 바로 고정할 수도 있다. 중요한 경험 목표는 **단지 순서를 옮기려던 동작이 의도치 않은 시각 고정으로 바뀌지 않는 것**이다.

드롭 영역, 보조키, 고정 버튼 등 구체적인 조작 방식은 후속 설계에서 정한다.

### 실행 순서는 기본 경로이지 명령이 아니다

위에 놓인 유동 블록은 다른 판단이 필요하지 않을 때 먼저 할 일이다. 사용자가 아래의 일을 먼저 끝내도 허용한다. 시간표와 다른 순서로 수행했다는 이유로 오류나 규칙 위반을 만들지 않는다.

앱은 공간을 잘 채우겠다는 이유로 사용자가 정한 순서를 몰래 뒤집지 않는다. 순서 변경과 업무 선택은 여전히 사용자의 판단이다.

---

## 5. 시간표의 새 의미: 과거 기록이 아니라 남은 일의 배치

### 완료된 유동 작업은 시간표에서 빠진다

시간표는 완료한 작업의 실제 수행 구간을 복원하는 장부가 아니다. 아직 해야 하는 유동 작업이 어느 정도 공간을 요구하는지 보여 주는 곳이다.

완료된 블록은 크기를 줄이거나 늘리지 않고 시간표 밖의 완료 영역으로 옮긴다. 블록의 정체성, 내용, 배분량과 관련 맥락은 보존한다. 시간표에서 제거하는 것은 삭제가 아니다.

상단 완료 영역의 위치도 과거의 특정 시각을 뜻하지 않는다. 그곳은 시간축 바깥의 보관 영역이다.

### 완료로 과거 시간을 되찾지는 않는다

60분 블록을 완료했다고 오늘의 전체 가용량에 60분이 더해지는 것은 아니다. 이미 지나간 시간은 그대로 지나갔다.

완료는 **앞으로 배치할 대상에서 그 작업을 제외하는 동작**이다. 남은 작업은 완료 확인 시점부터의 공간에 다시 놓인다. 과거의 빈자리를 채우려고 위로 당겨지지 않는다.

### 기본 사용에 수행시간 기록을 요구하지 않는다

완료 버튼을 누른 시각은 완료를 확인한 시각일 수 있다. 실제로 끝낸 시각이라고 자동 해석하지 않는다.

시작 버튼, 타이머, 일시중단, 작업별 실제 종료 시각 입력을 기본 사용의 전제조건으로 두지 않는다. 나중에 여러 일을 한꺼번에 완료해도 시간표가 정상적으로 정리되어야 한다.

## 6. 재배치 정책

### 6.1 완료하면 빠져나가고, 남은 일은 지금부터 다시 놓인다

오늘의 유동 작업을 완료하면 그 블록이 완료 영역으로 이동하고, 남은 유동 블록들이 해당 시점 이후의 가용 공간에 다시 놓인다.

이때 작업의 크기와 상대 순서, 고정 일정의 시각은 유지한다. 바뀌는 것은 이 조건들이 만들어 내는 **유동 블록의 예상 위치**다.

일괄 완료는 여러 블록을 함께 제외한 뒤 하나의 재배치 결과를 보여 준다. 사용자는 항목별 완료 순서나 실제 소요시간을 재구성하지 않는다.

### 6.2 수동 재배치는 새로운 판단 없이도 가능하다

완료한 일이 없어도 사용자는 `지금 기준으로 다시 배치`를 요청할 수 있다. 작업의 상태와 크기를 바꾸지 않고 현재 이후의 공간에서 배치를 갱신한다.

이 기능은 낡은 배치를 수리하라는 의무가 아니라, 지금 기준의 모습을 보고 싶을 때 사용하는 선택지다. 누르지 않았다고 계속 독촉하지 않는다.

### 6.3 시간이 흘러도 블록은 가만히 있다

현재선이 블록 안으로 들어오거나, 끝을 넘거나, 여러 미완료 블록을 지나가도 자동 재배치하지 않는다. 작업을 자동 완료하거나 크기를 늘리지도 않는다.

그 상태의 블록은 마지막으로 배치한 결과다. 현재선 뒤에 있다는 이유만으로 실제로 수행된 작업, 실패한 작업, 지각한 작업이 되지 않는다.

| 사건 | 이번 문서에서의 방침 |
|---|---|
| 현재 시각의 이동 | 시각 표현만 갱신한다. 블록은 움직이지 않는다. |
| 유동 블록의 시작·끝 경계 통과 | 자동 재배치나 수행 상태 변경을 하지 않는다. |
| 오늘의 유동 작업 완료 | 완료 영역으로 옮기고 현재 기준으로 재배치한다. |
| 여러 유동 작업 일괄 완료 | 선택 항목을 함께 옮기고 하나의 재배치 결과를 보여 준다. |
| 수동 재배치 | 작업 상태는 유지한 채 현재 기준으로 다시 놓는다. |
| 추가·삭제·순서 변경·고정 변경 | 사용자 조작에 맞는 배치 갱신은 필요하다. 현재 기준 전체 재배치까지 유발할지는 별도로 정한다. |
| 앱 복귀·재실행·자정·날짜 변경 | 그 자체를 자동 재배치 트리거로 추가하지 않는다. 날짜별 세부 정책은 후속 검토한다. |

계획을 편집한 결과를 화면에 반영하는 일과, 하루 전체의 배치 기준을 현재 시각으로 다시 잡는 일은 구분한다. 모든 편집을 무조건 전체 재배치로 연결해 불필요한 움직임을 만들지 않는다.

### 6.4 재배치가 대신하지 않는 판단

재배치는 무엇을 할지, 얼마나 할지, 어느 날 할지를 새로 결정하는 기능이 아니다. 공간 부족을 해소하려고 업무량을 축소하거나, 다른 날짜로 옮기거나, 집중 작업을 자동 분할하는 동작과도 구분한다.

어떤 배치 방법을 채택하더라도 **사용자가 내린 결정을 몰래 바꾸는 자동화**가 되어서는 안 된다.

## 7. 현재선과 재배치 경계를 분리한다

현재 시각은 계속 변한다. 마지막으로 블록을 놓을 때 사용한 기준은 다음 재배치 사건 전까지 유지된다.

기본 시간축은 위가 이르고 아래가 늦다. 따라서 재배치 시에는 현재 시각이 시간상의 하한이 되며, 새 유동 배치를 화면의 현재선 위쪽에 만들지 않는다. 이 기준은 재배치 순간에 적용하는 것이지, 현재선이 블록을 계속 밀어내는 움직이는 벽이 아니다.

평상시의 현재선은 **비접촉 표시선**이다. 블록을 관통할 수 있지만 힘을 가하지 않는다. 완료나 수동 재배치가 발생할 때만 그 시점이 새 배치의 경계로 작용한다.

두 기준이 다르다는 이유로 반드시 두 개의 굵은 선을 상시 노출할 필요는 없다. 사용자에게 필요한 것은 다음의 이해다.

> **시간은 흐르지만 계획은 가만히 있다. 끝낸 일을 정리하거나 다시 배치할 때, 지금부터 가능한 모습으로 갱신된다.**

이 원칙은 오늘의 재배치에 관한 것이다. 미래 날짜의 최초 배정이나 과거 날짜의 늦은 완료에 현재 시각을 기계적으로 적용하지 않는다. 이들의 구체적인 날짜 처리 방식은 별도로 정한다.

## 8. 물리적 은유: 사건이 있을 때만 작동하는 흡입식 정렬 장치

### 8.1 기본 모습

시간축은 위에서 아래로 흐른다. 유동 블록은 가능한 한 이른 가용 공간을 향해 모여 있다. 고정 일정은 시간 레일의 걸쇠에 붙어 있고, 완료 영역은 시간표 바깥 상단에 있다.

완료 사건이 발생하면 하나의 정리 동작이 일어난다.

**완료 블록이 빠져나감 → 그 시점의 가용 경계가 적용됨 → 남은 블록이 다시 자리 잡음 → 화면이 정지함.**

사용자가 보는 것은 복잡한 기계의 절차가 아니라, 자신이 끝낸 일이 사라지고 다음 일을 볼 수 있게 되는 변화다.

### 8.2 장치마다 설명하는 역할이 다르다

| 장치의 은유 | 설명하려는 원리 |
|---|---|
| 상단 흡입구·수거함 | 완료된 유동 작업이 시간 공간 밖으로 빠져나간다. |
| 상단으로 당기는 정렬력 | 남은 블록은 주어진 제약 안에서 이른 가용 공간에 모인다. |
| 브레이크·클러치 | 평상시에는 멈춰 있고, 완료나 수동 요청 때만 배치가 갱신된다. |
| 시간 레일의 걸쇠 | 고정 일정은 다른 블록의 변화에 밀리지 않는다. |
| 재배치 순간의 셔터 | 그 시점보다 과거인 공간에 새로 배치하지 않는다. |
| 우회 통로 | 고정 구조물을 움직이지 않고도 유동 블록이 다른 가용 구간으로 옮겨질 수 있다. |

이 장치들을 모두 실제 화면에 그릴 필요는 없다. 특히 클러치나 우회 통로는 동작의 일관성을 검토하기 위한 개념이며, 특정 그래픽이나 애니메이션 구현을 요구하지 않는다.

### 8.3 흡입 방향과 재배치 방향은 같지 않을 수 있다

완료된 블록은 위쪽 수거함으로 빠져나간다. 그러나 남은 블록은 빨리 완료했을 때 위로 당겨질 수도 있고, 늦게 완료했을 때 현재 이후의 공간으로 내려갈 수도 있다.

따라서 흡입력을 **언제나 모든 블록을 위로 이동시키는 힘**으로 표현하지 않는다. 먼저 현재 조건을 적용하고, 그 안에서 가능한 이른 자리에 정렬하는 원리다.

완료 블록이 수거함으로 빠져나가는 경로는 실행을 위한 시간 공간을 점유하는 경로도 아니다. 시각 효과 때문에 고정 일정이 움직이거나 충돌한 것처럼 보이지 않게 한다.

### 8.4 고정 구조는 영구적인 칸막이가 아니다

점심 아래에 있던 유동 블록도 앞쪽에 충분한 공간이 생기면 점심 위로 옮겨질 수 있다. 점심은 점유할 수 없는 구간이지, 작업을 오전과 오후에 영구적으로 소속시키는 경계가 아니다.

별도의 전후 조건이 필요하다면 그것은 추가적인 사용자 의도다. 단지 어느 쪽에 놓여 있었다는 이유로 그런 조건을 추론하지 않는다.

### 8.5 물리감은 이해를 돕는 만큼만 사용한다

흡입·이동·정착의 연결은 짧고 차분해야 한다. 큰 블록들이 화면 전체를 날아다니거나 완료 조작마다 긴 연출을 기다리게 하지 않는다.

움직임이 줄어들거나 없어도 완료와 재배치의 의미를 읽을 수 있어야 한다. 걸쇠도 색이나 재질만으로 구분하지 않고, 시각 고정이라는 의미를 확인할 수 있어야 한다.

## 9. 대표 사용자 경험

### 9.1 하루를 편성한다

사용자는 Inbox에 할 일을 담고, 계획할 때 예상 투입량을 정한다. 블록을 날짜에 던져 그날의 유동계획으로 만든다. 먼저 할 일이 있으면 앞쪽으로 옮긴다. 워크숍처럼 시각이 중요한 것만 고정한다.

이 단계에서 필요한 판단은 업무량과 가용량, 상대 순서, 실제 시각 제약이다. 모든 업무에 시작 시각을 붙이는 작업은 요구하지 않는다.

### 9.2 수행 중에는 앱을 관리하지 않는다

사용자는 일을 한다. 현재선은 움직이지만 블록은 자리를 유지한다. 앱이 활성 창이 아니거나 완료 체크를 한동안 하지 않았어도 작업을 끝났다고 추정하지 않는다.

사용자가 다음 일을 볼 때는 남은 블록의 순서와 크기, 고정 일정을 읽을 수 있다. 반드시 현재선 위에 있는 작업만 해야 하는 것은 아니다.

### 9.3 끝낸 일을 정리하면 공간도 함께 정리된다

작업을 완료하면 상단 완료 영역으로 빠져나간다. 남은 블록은 현재 기준의 가용 공간에 다시 놓인다.

사용자가 별도로 종료 시각을 입력하거나 앞뒤 블록을 이동할 필요는 없다. 일괄 완료도 같은 원리다.

### 9.4 완료 후에도 선택권은 남는다

사용자는 재배치된 첫 작업을 하거나 다른 작업을 먼저 할 수 있다. 정밀한 계획이 필요해지면 블록을 고정할 수 있고, 유연성이 필요해지면 고정을 해제할 수 있다.

완료 취소 시에는 같은 작업을 복귀시킬 수 있어야 한다. 복귀 순서와 재배치 범위는 후속 설계 대상이지만, 과거의 시각에 억지로 되돌려 놓거나 중복 작업을 만드는 경험은 피한다.

## 10. 조기 완료·늦은 완료·일괄 완료 시뮬레이션

다음 사례는 의도를 확인하기 위한 예시다. 배치 알고리즘이나 시간 눈금 표시 방식을 확정하지 않는다. 여기서는 순서를 유지하고 자동 분할하지 않으며, 들어갈 수 있는 가장 이른 연속 구간에 놓는다고 가정한다.

근무는 09:00–18:00, 점심은 12:00–13:00, 고정 일정은 14:00–15:00이다. 유동 순서는 A·B·C·D이며 크기는 각각 60분·45분·30분·60분이다.

| 상황 | 완료 영역으로 이동 | 남은 유동 배치 |
|---|---|---|
| 최초 배치 | 없음 | A 09:00–10:00 / B 10:00–10:45 / C 10:45–11:15 / D 13:00–14:00 |
| 09:40에 A 완료 | A, 크기 60분 보존 | B 09:40–10:25 / C 10:25–10:55 / D 10:55–11:55 |
| 10:20에 A 완료 | A, 크기 60분 보존 | B 10:20–11:05 / C 11:05–11:35 / D 13:00–14:00 |
| 11:30에 A·B·C 일괄 완료 | A·B·C, 각 크기 보존 | D 13:00–14:00 |

각 행은 최초 계획에서 갈라지는 독립적인 상황이다.

조기 완료와 늦은 완료는 같은 조작으로 처리한다. A가 실제로 40분 또는 80분 걸렸다고 기록하지 않는다. 완료 확인 시점에 A를 배치 대상에서 제외한 뒤 남은 일만 다시 놓는다.

일괄 완료에서도 지나간 시간을 A·B·C에 나눠 줄 필요가 없다. 11:30을 세 작업의 실제 완료 시각으로 간주할 필요도 없다.

반면 11:30까지 아무 동작도 하지 않았다면 최초 배치는 그대로 남는다. 여러 블록이 현재선 뒤에 있어도 자동 완료나 경계 기반 재배치는 발생하지 않는다.

## 11. 화면과 피드백의 목표

### 계획에서는 전체 배분, 수행에서는 남은 일을 읽는다

계획할 때는 어느 날에 얼마나 배분했는지, 고정 구조가 얼마의 공간을 차지하는지, 여유가 있는지 읽을 수 있어야 한다.

수행할 때는 다음에 할 일과 고정 시각의 제약을 쉽게 읽을 수 있어야 한다. 세밀한 시간 눈금이나 계산된 시작 시각은 필요에 따라 확인할 수 있지만, 항상 주의를 끌어야 할 정보는 아니다.

두 목적을 별도 화면으로 나눌지, 같은 화면의 정보 밀도를 바꿀지는 정하지 않는다.

### 완료 영역은 성과의 흔적이지 시간 장부가 아니다

완료 목록을 통해 끝낸 결과를 확인하고 다시 열거나 복귀시킬 수 있어야 한다. 접힘 여부, 상단 고정 여부, 완료 블록의 축약 방식은 시각 설계에서 정한다.

완료한 블록의 배분량을 합산하더라도 그것을 실제 노동시간이나 객관적 생산성 점수라고 부르지 않는다. 완료 건수 역시 가치 있는 산출을 대신하는 유일한 척도가 아니다.

### 낡은 배치를 오류처럼 꾸미지 않는다

현재선이 블록을 지났다는 이유로 빨간 경고, 지연 점수, 깜빡임, 강제 재조정 안내를 만들지 않는다. 필요하면 마지막 배치 기준이나 수동 갱신 동작에 접근할 수 있게 한다.

고정 일정의 실제 시각 제약과 유동 배치의 오래된 예상 위치는 다른 강도로 다룬다. 구체적인 알림 기능과 전달 방식은 이번 문서에서 확정하지 않는다.

### 움직임보다 사용자의 조작이 우선이다

재배치 때문에 읽던 내용, 입력 위치, 선택 대상이나 키보드 초점이 뜻밖에 바뀌지 않아야 한다. 연속 완료를 하다가 이동한 다른 작업을 잘못 누르는 경험도 피해야 한다.

개별 완료, 다중 선택, 일괄 완료 중 어떤 방식이 가장 안정적인지는 실제 사용 흐름으로 확인한다. 드래그 외의 조작 경로와 움직임을 줄인 표현에서도 같은 의미가 유지되어야 한다.

## 12. 단순화를 유지하기 위해 정직하게 남겨 둘 한계

### 일부 수행한 미완료 작업은 여전히 원래 크기다

2시간 블록을 상당 부분 수행했어도 완료하지 않았다면 재배치에서는 여전히 2시간을 요구한다. 남은 실제 분량을 모르는 상태에서 임의로 줄이지 않기로 했기 때문이다.

따라서 재배치 결과는 **미완료 블록의 배분량을 기준으로 한 배치**이지, 실제 잔여시간의 정밀 예측이 아니다. 이 차이를 숨기지 않는다.

잔여량 수정이나 부분 수행 표현은 이후 검토할 수 있지만, 그런 입력을 요구해야만 기본 동작이 성립하는 모델로 돌아가지 않는다.

### 공간에 들어가지 않는 일은 보이게 남는다

어떤 블록이 남은 공간에 들어가지 않아도 사라지거나 자동으로 내일로 넘어가서는 안 된다. 해당 날짜의 계획에 남아 있되, 현재 공간에 놓이지 못했다는 사실을 확인할 수 있어야 한다.

총량이 부족한 경우와 충분히 긴 연속 구간이 없는 경우는 다를 수 있다. 이를 구분해 판단을 도울 수 있지만, 빈칸을 채우라고 압박하거나 사용자의 순서를 자동 변경하지 않는다.

이 문서에서는 공간 부족 시의 세부 배치 순서, 대기 영역의 형태, 분할 제안 등을 확정하지 않는다.

### 고정 작업의 완료와 예약 해제는 같은 문제가 아니다

유동 작업의 완료는 미래 배치 대상에서의 제거다. 고정 일정은 특정 시각의 예약이기도 하므로, 완료 체크가 남은 예약까지 즉시 없애는지는 별도 판단이 필요하다.

고정 일정의 조기 종료, 취소, 불참, 지난 일정 확인을 하나의 완료 동작으로 뭉뚱그리지 않는다. 걸쇠가 붙은 블록의 공간 해제 정책은 후속 설계에서 정한다.

### 시각 효과보다 기록의 신뢰성이 먼저다

완료 블록이 빨려 나갔는데 완료 상태가 보존되지 않는 경험은 허용할 수 없다. 저장 실패나 복구 상황에서도 사용자가 무엇이 남았고 무엇이 완료되었는지 알 수 있어야 한다.

새 배치 은유를 도입하더라도 기존의 입력 보존, 오류 표시, 백업·복구의 의도는 약화하지 않는다. 구체적인 저장 순서나 기술적 처리 방식은 구현 설계의 영역으로 남긴다.

## 13. 후속 설계에서 결정할 질문

| 질문 | 지켜야 할 경험 목표 |
|---|---|
| 드래그로 순서 변경과 시각 고정을 어떻게 구분할까? | 사용자가 의도한 정밀도보다 더 강한 약속을 만들지 않는다. |
| 추가·삭제·고정 변경 시 어디까지 재배치할까? | 조작 결과는 반영하되 관계없는 작업까지 뜻밖에 움직이지 않게 한다. |
| 크기가 맞지 않는 블록과 빈 구간을 어떻게 다룰까? | 배치의 이유를 이해할 수 있게 하고, 순서·분할 판단을 몰래 대신하지 않는다. |
| 현재선과 마지막 배치 기준을 얼마나 보여 줄까? | 시간 감각은 유지하되 계획 오차에 대한 상시 감시 화면이 되지 않게 한다. |
| 완료 취소·날짜 이동·다른 날짜의 완료는 어떻게 연결할까? | 원래 맥락을 보존하고 의도하지 않은 날짜 변경이나 누락을 막는다. |
| 재실행·절전 복귀·자정에는 어떤 모습을 복원할까? | 시간 경과를 수행 사실로 바꾸지 않고, 조용한 자동 재계획을 도입하지 않는다. |
| 고정 일정이 실제로 일찍 또는 늦게 끝나면 어떻게 할까? | 업무 완료와 시각 예약을 구분하면서 공간을 해제할 통제권을 준다. |
| 일부 수행한 작업의 잔여량을 다룰까? | 선택적으로 정교해질 수 있되 타이머 관리가 기본 의무가 되지 않게 한다. |
| 흡입과 정착을 어떤 시각 효과로 표현할까? | 원인과 결과를 읽을 수 있게 하되 연출이 수행을 방해하지 않게 한다. |

저장 모델, 명령 체계, 상태기계의 세부 전이, 배치 알고리즘, 픽셀·색·재질·애니메이션 시간, 시간 눈금과 스냅 단위, 화면별 기본 설정은 이 문서에서 확정하지 않는다.

## 14. 설계가 성공했는지 확인할 기준

검증의 중심은 시간표의 정밀도가 아니라 **사용자가 계획을 유지하는 데 얼마나 적은 판단과 조작을 쓰는가**다.

| 확인할 장면 | 기대하는 이해와 행동 |
|---|---|
| Inbox에서 날짜로 블록을 놓음 | 시작 시각을 정하지 않아도 오늘 할 일로 충분히 계획되었다고 느낀다. |
| 현재선이 여러 미완료 블록을 통과함 | 오류나 완료를 뜻하지 않으며, 블록이 혼자 움직이지 않을 것이라고 이해한다. |
| 예상보다 빨리 또는 늦게 완료함 | 같은 완료 동작만으로 다음 배치가 정리되고, 소요시간 보정을 요구받지 않는다. |
| 여러 작업을 나중에 함께 완료함 | 과거 시간을 재구성하지 않고 남은 일을 계속 처리할 수 있다. |
| 남은 블록이 이전보다 아래로 이동함 | 벌점이나 지연 연출이 아니라 현재 이후 공간에 다시 놓인 결과로 이해한다. |
| 점심·워크숍을 사이에 둔 재배치 | 고정 구조는 유지되고 유동 작업만 달라졌음을 읽을 수 있다. |
| 공간이 부족하거나 빈 구간이 생김 | 조정할 수 있는 정보로 받아들이며, 강제 분할이나 자동 이월을 경험하지 않는다. |
| 완료 취소 또는 저장 실패 | 작업을 잃거나 잘못된 완료 상태를 믿게 되지 않는다. |
| 움직임을 줄이거나 키보드로 조작함 | 물리적 연출 없이도 같은 계획·완료·재배치 관계를 이해한다. |

실사용에서는 하루 계획을 세우는 부담, 완료 후 추가 조정의 필요, 잘못된 선택과 되돌림, 불필요하게 시간표를 다시 확인하는 행동을 관찰한다. 동시에 계획이 실제 업무 선택과 산출에 도움이 되었는지도 함께 살핀다.

이러한 관찰을 위한 연구 기록과, 사용자를 매일 평가하는 점수판은 구분한다. 성공 기준을 얻기 위해 또 다른 관리 의무를 사용자에게 부과하지 않는다.

## 15. 한 문장으로 정리한 방향

> **사용자는 업무의 양과 순서, 지켜야 할 시각을 결정한다. BLOKKY는 그 결정을 가용 공간에 놓고, 완료된 일만 밖으로 거둔 뒤 남은 일을 지금부터 다시 정렬한다.**

시간은 계속 흐르지만 블록은 계속 움직이지 않는다. 완료했다고 과거의 시간을 측정하거나, 아직 완료하지 않았다고 지연을 판정하지 않는다.

정밀하게 계획할 자유는 남긴다. 그러나 정밀하게 계획하고 계속 고쳐야만 사용할 수 있는 시스템으로 만들지는 않는다.

**계획의 유용성은 유지하고, 계획을 유지하는 노동은 줄인다.**
