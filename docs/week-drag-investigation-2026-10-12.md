# 계획 주 뷰 드래그 중단 조사

2026-10-12, 조사 대상 커밋 `ff590de`. 범위는 재현과 원인 특정이며 제품 코드는 수정하지 않았다.

## 후속 수정

사용자의 수정 지시 후 `DaySpace`가 소유한 날짜를 `Block`에 전달하고 draggable ID를 `${variant}:${date}:${t.id}`로 분리했다. 날짜별 인스턴스가 서로의 등록을 덮어쓰지 않으며, 저장에 쓰는 `data.taskId`와 퇴장 애니메이션은 유지한다.

기존 `scripts/ui-check/plan.mjs`에 빠른 날짜 왕복 → 놓기 → 재드래그 → 다시 왕복 → Escape 취소 → 재드래그·다른 날짜 저장을 확인하는 시나리오 하나를 추가했다. 출발지·목적지 블록이 동시에 존재할 때 복귀하는지도 확인한다. 수정 전 재드래그 단언 실패, 수정 후 통과를 확인했다. 아래 내용은 수정 전 조사 기록이다.

## 결과

주 뷰에서 블록을 옆 날짜의 본문으로 끌었다가 원래 날짜로 빠르게 되돌리면, 블록은 보이지만 dnd-kit의 draggable 등록이 사라진다. 이후 같은 블록을 끌어도 시작되지 않는다. 오늘 탭으로 갔다가 계획 탭으로 돌아오면 등록과 드래그가 복구된다.

## 재현

1. 개발 미리보기 `/?now=10:20`에서 계획 → 주를 연다. 진단에서는 미계획 드로어를 닫았다.
2. 오늘의 ‘설계 문서 자료 조사’ 본문을 잡아 5px 이상의 활성화 거리를 넘긴다.
3. 옆 날짜 본문으로 수평 이동한다. 블록의 열 안 상대 위치를 유지해 고정 레일에 붙지 않게 한다.
4. 약 40ms 뒤 원래 날짜 본문으로 돌아오고, 250ms 기다린 다음 놓는다.
5. 같은 블록을 다시 끌면 복사본이 나타나지 않는다. 오늘 → 계획 탭 전환 후에는 다시 끌린다.

40ms는 진단 입력의 대기 시간이며 보편적인 임계값을 측정한 결과는 아니다. 실제 조건은 출발지 블록의 퇴장 애니메이션이 끝나기 전에 복귀하는 것이다. 고정 레일은 미리보기 지연이 있으므로 본문 왕복과 조건이 다르다.

## 관측 근거

기존 `scripts/ui-check.mjs`의 격리된 headless Edge와 실제 CDP 마우스 입력을 사용했다. 임시 진단 시나리오에서 React context의 `draggableNodes`를 읽기만 하고, 다음 드래그 때 `.blk.held`가 생기는지도 별도로 확인했다. 저장소 데이터는 개발 미리보기의 샘플이다.

| 단계 | 블록 DOM | `column:sample-a` 등록 | 다음 드래그 복사본 |
|---|---|---|---|
| 시작 | 있음 | 있음 | 최초 드래그 활성화 |
| 옆 날짜 체류 40ms 후 복귀·놓기 | 있음 | 없음 | 0개 |
| 오늘 → 계획 탭 전환 | 있음 | 있음 | 1개 |
| 대조: 옆 날짜 체류 300ms 후 복귀·놓기 | 있음 | 있음 | 1개 |

빠른 왕복 진단은 4.999초, 느린 왕복 대조는 5.311초에 각각 기대한 관측을 모두 통과했다. 여기서 통과는 결함과 대조 조건을 확인했다는 뜻이며 버그 수정 완료를 뜻하지 않는다. 콘솔 오류도 없었다.

## 원인

- `src/app/space/DaySpace.tsx:109`: 날짜마다 별도의 `AnimatePresence`가 블록을 관리한다.
- 같은 파일 `:172`: draggable ID가 `${variant}:${t.id}`이므로 같은 작업의 출발지·목적지 인스턴스가 `column:sample-a`를 공유한다.
- 같은 파일 `:190`: 일반 퇴장 애니메이션은 0.12초 동안 이전 인스턴스를 유지한다.
- `src/app/space/drag.tsx:100–103`: 드래그 미리보기부터 `applyIntent`로 날짜별 표시 작업을 바꾼다.
- 설치된 `@dnd-kit/core`의 `dist/core.esm.js:3415–3433`: 등록 effect는 `[draggableNodes, id]`에 의존하며 cleanup은 현재 등록의 인스턴스 key가 자기 key일 때 삭제한다.

실제 순서는 다음과 같다.

1. A 날짜에서 B 날짜로 이동하면 B의 새 인스턴스가 동일 ID의 등록을 덮어쓴다. A는 퇴장 중이다.
2. A의 퇴장이 끝나기 전에 돌아오면 기존 A 인스턴스가 재사용된다. ID가 변하지 않아 등록 effect가 재실행되지 않는다.
3. B의 퇴장이 끝나면 B가 자신이 소유한 등록을 삭제한다. A는 화면에 남지만 등록은 없다.
4. dnd-kit은 `core.esm.js:3180–3187`에서 등록 없는 ID의 활성화를 무시한다.
5. `src/app/shell/Shell.tsx:63`의 탭 전환은 Plan을 재마운트해 블록을 다시 등록한다. DragProvider 자체를 초기화하지 않아도 복구된다.

단순히 이전 인스턴스의 cleanup이 새 등록을 지우는 문제는 아니다. dnd-kit의 key 검사가 그 경우를 방어한다. 퇴장 중 원래 인스턴스가 되살아나고, 마지막 등록자였던 다른 인스턴스가 사라지는 조합이 핵심이다. 300ms 대조에서는 A가 먼저 제거되므로 복귀 때 새로 등록되어 정상이다.

## 후속 수정 범위와 검증 한계

후속 수정은 같은 작업의 서로 다른 날짜 공간 인스턴스가 draggable ID를 공유하지 않도록 하는 방향이 우선 후보다. 작업 식별자는 기존 `data.taskId`로 분리되어 있다. 수정 시 빠른 왕복·일반 날짜 이동·취소·탭 복귀를 기존 plan UI owner에서 검증해야 한다.

이번에는 앱 수정이나 영구 회귀 테스트를 추가하지 않았다. 실제 설치된 Windows Tauri 앱에서 직접 재현하지 않았으며, 브라우저에서 공유 React UI의 동일 증상과 등록 소실을 확인했다. 사용자가 겪은 모든 간헐적 드래그 중단의 원인이 이것 하나라고 단정하지 않는다.
