# 캘린더 품질 개선 실행 계획

2026-10-09 품질 보고서의 40개 시험을 기준으로 계획하고, 사용자 요청에 따라 1단계부터 착수했다. [현재 진단](calendar-quality-report-2026-10-09.md)은 수정 전 증거다. 지원 범위 선택 질문에 아직 답이 없어 **첨부 원문 40개 목표를 최종 목표로 계획**하되, 현재 구현은 즉시 결함 수정에 한정한다. 이것은 미지원 기능을 제외하기로 승인받았거나 반복·알림의 세부 정책이 승인되었다는 뜻이 아니다.

## 1단계 구현과 검증

- 로드 실패에도 백업 관리가 표시되며 기존 목록·검사·오류·큐 재시도를 재사용한다. 새 백업 생성은 정상 저장소에서만 가능하다. 복구 교체는 손상 자료 보존을 확인하고, 동일 백업 ID 재시도와 성공 응답 뒤 정상 화면/포커스 이동을 유지한다.
- 조합 판정을 공유하고, 오늘/계획의 안전한 재렌더 gate를 추가했다. 새 테스트 파일/의존성 없이 기존 owner를 확장했다.
- 현재 자동 검증: `npm test` **18/18**, 러너123.371ms; 단독 프런트 build218ms. 최종 Rust **13/13** 본체3.67초 및 desktop cargo check1.25초 통과. `./scripts/run.ps1 package`에서 TypeScript/Vite282ms, Rust release20.36초, NSIS 패키징 성공. 이는 전체 UI/IME 합격이 아니다.
- 리뷰에서 복구 완료 후 포커스 재손실을 수정했다. 실제 Store 로드 실패만 복구 화면으로 보내고, 초안/운영 정보 오류는 별도 상태와 다시 불러오기로 처리한다. 복구/로드 재시도 성공 시 운영 정보를 갱신한다.
- 초안 읽기 실패는 Store-ready와 별도로 편집/초안 쓰기/정상 복원을 차단한다. 읽어 둔 sequence는 JSON 해석 전에 보존하고, 읽기 자체가 실패한 경우 새 sequence를 발급하지 않는다. 해석만 실패한 보관 초안은 사용자가 확인 후 버릴 수 있다. 캡처창 재조회 성공 때에는 보관 텍스트를 표시한 뒤 입력을 활성화한다.
- 격리 Windows 앱에서 손상 DB의 백업 목록→2건 검사→교체 확인→복구→근무 설정 복원을 확인했다. 최종 fixture의 원본과 archive DB/WAL/SHM3파일 해시가 모두 같고 `.recovering`은 남지 않았다. 별도 정상 DB의 잘못된 메인/캡처 초안은 sequence7을 유지하며 편집을 막았고, 시험 측에서 sequence8로 정규화한 뒤 실제 다시 불러오기가 정상 화면과 캡처 보관 텍스트를 표시했다.
- 초기 실패 open의 WAL/SHM 제거 문제도 실제 실행에서 발견해 임시 복사본 preflight로 수정했다. 원본 검증과 시작 성능을 함께 고려해야 하며 새 startup I/O의 정식 성능 영향은 미측정이다. 독립 실행 파일/데이터로 확인한 상세 범위와 제한은 [검증 기록](../validation.md)에 있다.
