## Design specificity

The composition is recognizably authored for personal time blocking: a chronological execution list beside proportional time blocks, unavailable periods, and a multi-week capacity view feeding a selected day's schedule. Those structures would not transfer unchanged to an unrelated CRUD dashboard. The restrained blue and gray palette and familiar Windows controls appropriately support repeated work. They are not a reason to invent a new visual language. The main opportunity is clearer context and recovery in existing interactions, not greater visual novelty.

## Strengths

1. Today separates “what comes next” from “how much time it occupies.” Completion appears both as a checked/list-struck item and a labeled gray block, avoiding reliance on color alone.
2. The planning calendar encodes capacity rather than decorative task summaries. The selected day and unavailable periods make the scheduling model concrete; Inbox offers dragging and opening an item as alternatives.
3. Empty days provide an immediate “계획 열기” path, while the always-available capture input supports interruption-heavy work without forcing the user to schedule immediately.

## Priority issues (maximum three)

### P2 — Settings recovery does not locate or retire the error

**Observed:** Entering `점심` in Monday's “작업 불가 시간” and pressing “시간 설정 저장” produces the bottom message `작업 불가 시간은 “12:00-13:00 점심” 형식으로 입력하세요.` The submit button is at the bottom of a long form; the invalid Monday field is off-screen. The message does not name Monday or a line. Clicking “변경 버리기” restores the valid original values, but the same error remains visible.

**Why it matters:** Users must search seven repeated fields, and after choosing the recovery action the app still appears broken. This is a bounded annoyance with a workaround, not evidence of lost data.

**Fix:** Include weekday and line in the parser error, associate it with the field and move focus to that field on submit. Clear only the settings validation error when that draft is discarded or successfully corrected. Preserve unrelated storage errors.

**Source support:** `readSettings`, `bindSettings` and shared `errorMessage` in `src/main.ts`.

**Suggested commands:** `clarify`, `harden`.

### P2 — The today label can describe a different date

**Observed:** On 2026-10-08, pressing the next-period arrow in Today changes the top date to 10월 9일 금요일 and displays that day's empty data, while the panel heading remains “오늘 순서.”

**Why it matters:** A user returning from date exploration has two contradictory descriptions of the schedule. The actual date is present, so the user can recover, but the primary execution context should not require reconciling labels.

**Fix:** Keep “오늘 순서” only for today; use the selected date or a neutral day-order label otherwise. Consider making the rail's “오늘” entry explicitly return to today if that is its product meaning. Do not alter the approved two-panel layout.

**Source support:** `todayHTML` uses a fixed heading; navigation changes the shared `selected` date.

**Suggested command:** `clarify`.

### P2 — At 960×640 the detail editor hides the save action below a large blank memo

**Observed:** Opening an Inbox item's detail at the minimum supported size shows title, date, duration, and a nearly 300px-tall blank memo. “변경 저장,” completion, and the saved/unsaved status are below the initial dialog viewport. When the save control is brought into view, the title and top close button scroll away.

**Why it matters:** A quick date/time edit requires extra scrolling before the main action can be found, and the item identity disappears at the commit point. The dialog remains scrollable and functional; it is not a blocking overflow defect.

**Fix:** Use a shorter initial memo at short desktop heights, or keep a compact primary action/status area visible while the form scrolls. Retain a resizable memo and the established dialog appearance; do not turn the task into a modal redesign.

**Source support:** `renderEditor` uses `rows="12"`; the dialog is capped at `100vh - 48px` and its actions follow the memo.

**Suggested commands:** `adapt`, then `polish`.

## Cognitive load

Observed load is moderate in the secondary edit/setup flows and low in ordinary capture/complete use. Checklist: single focus passes; chunking passes through weekday fieldsets and action rows; grouping passes; visual hierarchy passes generally; one thing at a time passes; minimal choices is a partial failure; working-memory support fails during settings-error recovery; progressive disclosure passes through the Inbox and editor. Two failures/partial failures rather than a blanket “overloaded” judgment.

Decision points with more than four visible options: the editor exposes six actions once scrolled down (three primary/task actions and three secondary actions); settings exposes seven weekday groups. The calendar has 14/28/42 dates, but a familiar spatial calendar is not equivalent to dozens of unrelated menu options and should not be collapsed merely to satisfy a numeric rule. At 960px Inbox replaces the calendar while retaining the selected date above the timeline; this is an intentional, workable density tradeoff, not by itself a defect.

## Emotional journey

Capture gives a clear acknowledgment and completion updates the count and block treatment: these are quiet, useful positive endpoints. No additional celebratory motion is needed; dependable feedback is more appropriate for this product.
